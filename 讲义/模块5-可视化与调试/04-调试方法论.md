> 单集约 12 分钟 · 模块 5 第 4 集 
> 前置：5.1–5.3 已会 rqt / ros2 bag / 分级日志。本集是模块 5 的收官实战。

## 一、本集目标

独立定位并修好三类经典故障：

| 类型 | 现象 | 典型原因 |
| ---- | ---- | -------- |
| **不说话** | 没数据 | 节点没起 / 话题名不一致 |
| **说错话** | 有数据但不对 | 类型不匹配 / 值异常 / 解析失败 |
| **说晚了** | 有数据但太慢/太旧 | 频率太低 / QoS / 时间戳 |

用一张**检查清单**按顺序排查，10 分钟内修完 3 个埋好的 bug。


## 三、理论讲解

### 3.1 调试第一原则：先观察，后改代码

新手三大作死操作：

1. 不看 `ros2 node list` 就改代码；
2. 一次改五处，不知道哪处生效；
3. 凭感觉猜"应该是 QoS 吧"，直接改 QoS。

正确姿势：**每一步只验证一个假设，改一处，再验证**。

### 3.2 七步检查清单（背下来）

按顺序做，跳步 = 漏诊：

| 步 | 命令 | 回答什么问题 |
| -- | ---- | ------------ |
| 1 | `ros2 node list` | 节点在不在？名字对不对？ |
| 2 | `ros2 topic list` | 话题在不在？ |
| 3 | `ros2 topic hz <t>` / `ros2 topic echo <t>` | 有没有数据？频率多少？ |
| 4 | `ros2 topic info <t>` + `ros2 interface show <T>` | 类型/字段对不对？ |
| 5 | `ros2 topic info -v <t>` | QoS 配不配得上？ |
| 6 | `ros2 param get` / 检查 `use_sim_time` | 参数/时间对不对？ |
| 7 | `rqt_console` / 日志级别 | 日志说了什么？ |

对应关系：

```text
不说话 → 卡在 1~3
说错话 → 卡在 4、6、7
说晚了 → 卡在 3（hz）、5（QoS）、6（时间）
```

### 3.3 三类问题的思维导图

```text
没数据？
  ├─ node list 空 → 节点没起来（看 launch / entry_points / 日志）
  ├─ 节点在、话题不在 → create_publisher 名字错
  └─ 话题在、echo 空 → 对端没发 / 话题名不一致 / QoS 不配

有数据但不对？
  ├─ 类型不匹配 → info 看 Type，interface show 对字段
  ├─ 解析失败 → 消息格式契约被破坏（看 warn 原始内容）
  └─ 数值离谱 → 上游逻辑或参数错（param get 阈值）

有数据但太慢？
  ├─ hz 远低于预期 → 发布频率参数 / timer 周期
  ├─ 突然卡住 → 回调阻塞 / 刷屏
  └─ 时间戳不对 → use_sim_time 与仿真时钟
```

### 3.4 QoS 为什么排在第 5？

入门阶段默认 QoS（Reliable + Volatile）通常能通。
只有 1–4 都正常却仍收不到时，才用 `ros2 topic info -v` 看：

| 项 | 典型坑 |
| -- | ------ |
| Reliability | pub Reliable + sub Best Effort 一般能通；反向不行 |
| Durability | sub 要 Transient Local 才收得到"发过的旧消息" |
| History/Depth | 深度太小会丢 |

### 3.5 时间：use_sim_time

仿真里节点必须 `use_sim_time:=true`，否则时间戳和 TF 全乱——"说晚了"的隐藏大 boss。本课真机/模拟节点用系统时钟即可，但清单里要留一位。

## 四、实操步骤（手把手 · 三个 bug 实战）

> 教练演示：如何把 bug **埋进** `my_bringup` 再按清单修好。 
> 你也可以只做"修"的部分——对照仓库正确代码 diff。

### 步骤 0 · 打开两个终端

都执行：

```bash
source /opt/ros/jazzy/setup.bash
source ~/ros2_ws/install/setup.bash
```

**预期**：两边命令正常。

### 步骤 1 · 埋 Bug A（不说话）：决策节点不发布

打开 `~/ros2_ws/src/my_bringup/launch/demo_system.launch.py`，把 decision_node 的 `executable` 故意改错：

```python
Node(
    package='my_bringup',
    executable='decision_node_typo',   # 故意写错
    name='decision_node',
    output='screen',
    parameters=[params_file],
),
```

**预期**：保存后 launch 会报错或该节点缺席。

### 步骤 2 · 埋 Bug B（说错话）：检测消息格式被破坏

打开 `my_bringup/sim_sensor.py`，把发布内容改掉：

```python
msg.data = f'{distance}'   # 破坏契约：少了 "distance="
```

**预期**：下游 `msg.data.split('=')[1]` 会解析失败。

### 步骤 3 · 埋 Bug C（说晚了）：频率被调到很低

打开 `config/params.yaml`：

```yaml
param_node:
  ros__parameters:
    publish_frequency: 0.2   # 故意调得极慢
    topic_name: /heartbeat
```

**预期**：心跳约 0.2 Hz（5 秒一条）。

### 步骤 4 · 编译并启动故障现场

```bash
cd ~/ros2_ws
colcon build --packages-select my_bringup --symlink-install
source /opt/ros/jazzy/setup.bash
source ~/ros2_ws/install/setup.bash
ros2 launch my_bringup demo_system.launch.py
```

**预期**：能启动，但现象如"二、效果演示"所述。

### 步骤 5 · 清单第 1–2 步：节点与话题

终端 B：

```bash
ros2 node list
ros2 topic list
```

**发现 A**：

- 若 launch 直接报 `Executable 'decision_node_typo' not found` → 锁定 executable 写错；
- 若节点列表里**没有** `/decision_node`，但 `/detection`、`/cmd_vel` 话题仍在（可能只有 pub 没有 sub）→ 同样怀疑可执行/节点名。

**预期（诊断）**：你已经能说出"不说话是因为决策节点没起来"。

**修复 A**：把 executable 改回 `decision_node`，重 build，重 launch。

**预期**：`ros2 node list` 出现 `/decision_node`。

### 步骤 6 · 清单第 3–4 步：数据与类型

```bash
ros2 topic echo /detection --once
ros2 topic info /detection
ros2 interface show std_msgs/msg/String
```

**发现 B**：echo 内容是 `0.83` 而不是 `distance=0.83`；类型仍是 String（类型没错，**内容契约**破了）。看日志/`rqt_console`：

```text
[WARN] [decision_node]: 无法解析检测消息: '0.83'
```

**预期（诊断）**：不是类型问题，是格式/解析问题。

**修复 B**：`sim_sensor.py` 改回

```python
msg.data = f'distance={distance}'
```

重 build（symlink 可能免），重启 launch。

**预期**：warn 消失，`/cmd_vel` 的 `linear.x` 开始 0.0/0.2 跳变。

### 步骤 7 · 清单第 3 步：频率（说晚了）

```bash
ros2 topic hz /heartbeat
ros2 param get /param_node publish_frequency
```

**发现 C**：`hz` 约 0.2；参数值 `0.2`——不是代码死循环卡，而是**参数配错**。

**预期（诊断）**：YAML 把频率调坏了。

**修复 C**：`params.yaml` 改回

```yaml
publish_frequency: 5.0
```

重 launch。

**预期**：`ros2 topic hz /heartbeat` 约 **5 Hz**。

### 步骤 8 · 清单第 5–7 步：QoS / 参数 / 日志扫尾

```bash
ros2 topic info -v /cmd_vel
ros2 topic hz /cmd_vel
rqt_console
```

**预期**：QoS 为默认 Reliable/Volatile；无 Error；Warn 仅在障碍过近时出现。

### 步骤 9 · 录一份"正常基线"

```bash
ros2 bag record -o ~/my_bringup_baseline /detection /cmd_vel /heartbeat
# 跑 15 秒 Ctrl+C
ros2 bag info ~/my_bringup_baseline
```

**预期**：Messages 均 > 0。以后改代码，play 这份 bag 对比，心里有底。

## 五、关键 API / 命令详解

| 名称 | 作用 |
| ---- | ---- |
| `ros2 node list` | 第 1 步：节点是否存在 |
| `ros2 topic list` | 第 2 步：话题是否存在 |
| `ros2 topic hz/echo` | 第 3 步：有没有数据、多快 |
| `ros2 topic info` / `interface show` | 第 4 步：类型与字段 |
| `ros2 topic info -v` | 第 5 步：QoS 详情 |
| `ros2 param get` | 第 6 步：参数是不是被改坏 |
| `rqt_console` / `get_logger()` | 第 7 步：异常是否已自陈 |
| `ros2 bag record/play/info` | 录基线、回放复现 |
| `use_sim_time` | 仿真时钟开关（时间类问题） |

---

## 六、常见坑

| 报错 / 现象 | 原因 | 解法 |
| ----------- | ---- | ---- |
| 不看 node list 就改代码 | 没定位到层 | 严格按清单 1→7 |
| 一次改很多处 | 无法归因 | 一次一个假设 |
| 报错原文不看，凭猜 | 走弯路 | 把终端报错整段读完再动手 |
| 改完不重 build / 不重启 | 假修复 | build → source → 重新 launch |
| 把 QoS 当万能药 | 真凶是话题名 | 先 1–4 再动 QoS |
| 仿真里忘 `use_sim_time` | 时间全乱 | 仿真节点统一 true |
| 只改代码不录基线 | 修好也说不清 | 回归用 bag 对比 |
